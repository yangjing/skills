按照 yangjing 的既有风格撰写中文技术博客文章。风格源自 source/_posts/ 下 140+ 篇已发布文章（2010-2026），涵盖 Scala、Java、Akka、Rust、gRPC、AI、随笔等类型。

<核心风格>
## 核心写作风格（最重要，优先遵循）

### 1. 问题驱动，直接开头
- 开头一至三句话进入正题：真实场景、真实痛点，或一句话说明本文做什么
- 不加"前言"章节（140+ 篇里只有 1 篇有），不做宏观铺垫
- 坏：在当今数据驱动的时代，数据的实时性成为了企业成功的关键……
- 好：最近两年技术书的出版速度明显更快了，书多了，根本读不过来。

### 2. 第一人称经验流，有态度
- "我"高频出现，直接下判断，敢表达个人偏好，偶尔口语化（翻车、折腾、说白了、大块头、一家之言、干货），但整体克制
- 好：在我眼里，Python 算不上好，我觉得他就是一个打了很多补丁、且补得一般般的感觉。但他够用、方便、灵活，这就够了！
- 不追求客观中立、面面俱到；有取舍、有立场才是这个博客的风格

### 3. 具体，有细节
- 多给具体数字：版本号、耗时、页数、命令输出（"一本 300 页左右的书，完整翻译大概 15-30 分钟"）
- 具体年数优于"多年"；真实踩坑经历优于泛泛最佳实践
- 分享文档之外的实战经验，官方文档能查到的就给链接、不复述

### 4. 短段落、短句
- 段落一般 1-3 句，技术讲解段最多 4-6 句
- 长句拆短；少用连接词，靠内容本身衔接
</核心风格>

<文章结构>
## 文章结构与元数据

### 站点元数据（frontmatter、文件名、分类：可选特性，依目标站点而定）

frontmatter YAML 是 Hexo 这类博客系统的要求，不是写作风格本身，也不是所有文章系统都有。处理元数据前，按优先级取约定：

1. **站点 overlay**：查找当前项目 `.agents/skills/` 下的 `doc-writer-style.overlay.md`（技能装在项目内时即技能目录旁；技能装在用户目录时仍以项目为准）。overlay 可覆盖本 skill 的任何默认约定，或对某项格式做出明确要求，命中即以其为准；通用规则留在 skill，不在 overlay 里复制
2. **Hexo 通用参考**：目标确认是 Hexo 站点且无 overlay 时，读 `references/hexo-frontmatter.md`。Hexo 7 实测兼容两种分隔写法（标准 `---` 包裹与省略开头 `---`），结尾 `---` 不能省
3. **都没有**：沿用目标站点已有文章的格式；仍无法判断时问用户，不猜测

### 五种文章类型模式

**实战教程**：背景/需求 → 环境准备 → 核心实现（带代码）→ 运行测试 → 常见问题 → 小结
例："使用 Crawl4AI 抓取搜狐文章教程"

**架构设计**：目标/问题 → 概念定义 → 架构图 → 技术选型及理由 → 实现要点 → 小结
例："通用分布式任务调度系统设计"

**经验总结**：背景 → 遇到的问题 → 解决方案 → 最佳实践
例："AI 协作编程 SOP：架构师驱动 + 结对编程模式"

**技术选型**：先亮态度 → 各选项对比 → 适用场景 → 个人经验 → 简短收尾
例："我会做的技术选型"

**随笔/感想**：一句话点题 → 松散结构（2-3 个二级标题即可）→ 列表化 → 个人判断或展望收尾。篇幅短、无代码、常带书名号和外部链接
例："迈向 2025"、"人是循环"

**翻译**：标题加"译-"前缀，保留原文结构与代码，译文遵守本 skill 的语言排版规则
例："译 akka-grpc 0.8.0 released"

### 关于"小结"
- 技术文常用 `## 小结` 收尾（近年约 80%），内容是一段实在的经验总结或个人态度，不写空洞套话
- 随笔、选型文经常没有小结标题，直接正文收尾，或以展望、挖坑（"后面会……"）结束
- 结尾给出个人判断（"这些都是我的一家之谈，并不适合每个项目和团队，但至少可以做为参考"）比"综上所述"式总结好得多
</文章结构>

<语言与排版>
## 语言与排版规则

- **中文正文用全角标点**（，：！？、）；中文句子中夹英文单词或代码时，包裹它们的括号用半角 `()`，纯中文内容才用全角（）；中英文之间加空格
- **技术术语保留英文**：Akka、Future、gRPC、epub，不翻译也不音译（不写"阿克卡框架"）
- **粗体是主要强调方式**：用于关键结论、警告、术语首次定义（"**杀手级** 功能"）
- **几乎不用斜体**：仅系列文章衔接说明或免责声明可用
- **行内代码** `code` 用于函数名、命令、文件名
- **标题层级**：正文从 `##` 开始，子节 `###`；正文不重复文章大标题（title 已在 frontmatter 里，直接进入正文或第一个 `##`）
- **第二人称用"你"**，不用"您"
- **不用 emoji**
- 架构图：简单结构用 Mermaid；需要更丰富的视觉效果和高保真输出时用 SVG 绘制（矢量、缩放不失真）；位图（PNG 等）放 /img/ 下，并配 alt 文字
</语言与排版>

<代码与链接>
## 代码与链接（均为可选，视文章类型和真实素材而定）

### 代码示例
- 教程、实战类通常需要代码，占比可达 40-60%；经验、选型、随笔类可以完全没有代码（历史文章约 22% 无任何代码块）
- 有代码时给**完整可运行**的示例而非碎片；shell 命令附真实输出；复杂处加中文注释；对比场景用 Before/After
- 代码块必须标语言（scala、rust、python、sh、sql……）

### GitHub / Gitee 链接
- **仅当 GitHub/Gitee 上确有对应仓库时才附**，绝不编造链接（历史文章约 73% 没有 GitHub 链接）
- 惯用句式，放在文末或小结："本文示例的完整代码见： https://github.com/yangjing/..."
- 参考链接给官方文档或一手来源即可
</代码与链接>

<AI味检查清单>
## AI 味检查清单（逐类给出替换方案，写完必须逐条检查）

AI 味的本质是用"训练数据的平均风格"写作：标准、工整、滴水不漏，但没有个性。对策不是删句式，而是用上面的核心风格盖过去。

这份清单不是禁用词表，命中某个词不等于必须删。判断顺序：① 这句话有没有具体信息 ② 是否符合当前文章体裁 ③ 它是否替代了事实、动作、边界或判断 ④ 删掉它后信息是否减少。有真实功能的表达保留，只删让文章"看起来完整"但没有信息增量的部分。

### 开头
- 坏："在当今……的时代"、"随着……的快速发展"、"近年来……日益重要" → 好：直接从真实场景或问题切入
- 坏："本文将介绍/深入探讨……"式将来时套话 → 好：一句话直述本文做什么（现在时，如"本文章分享如何在……"），然后直接开讲

### 用词
- 坏：赋能、闭环、抓手、底座、降本增效、生态（泛用时） → 好：说具体做了什么事
- 坏：至关重要、举足轻重、深刻变革、有力见证、显著提升、全面赋能、深入剖析 → 好：平实动词（很好用、性能提升明显、解决了我的问题）
- 坏：四字成语堆砌（与时俱进、行之有效、博大精深） → 好：日常用语

### 句式
- 坏："不仅……而且……"、"不是……而是……"、"与其说……不如说……"这类否定平行结构 → 好：直接说它是什么
- 坏：三连排比（"更快速、更安全、更可靠"）、列表硬凑第三条凑数 → 好：只留最有信息量的一两个，两条就两条
- 坏：首先/其次/最后、与此同时、值得注意的是、综上所述、总而言之 → 好：自然过渡或直接删除连接词
- 坏：假问题转场（"那么，什么才是真正的 X？"、"这背后意味着什么？"） → 好：直接给判断标准或待验证的假设
- 坏：抽象名词堆叠（"能力建设、路径优化、体系完善"，名词越多动作越少） → 好：拆成执行者、动作、对象、代价
- 坏："既有机遇，也有挑战"、"不能一概而论" → 好：明确说结论和适用条件
- 坏：每句都修饰到位、滴水不漏 → 好：允许口语和不完美，"这就够了！"比"具有较强的实用性"好

### 结构与节奏（文章级，比词句更容易露馅）
- 坏：每段结尾都补"这说明……"式总结、每节都落一句金句 → 好：让事实自己成立，全文只留一两处真正的收束
- 坏：句长像尺子量过（每句都 15-20 字，节奏均匀） → 好：长短交错，偶尔一个极短句（"这速度有点吓人。"）
- 坏：信息密度均匀，每一点等权重展开 → 好：感兴趣的大书特书，无所谓的带过，可以明说"这几条分量不一样"
- 坏：结构能被读者预判（背景→特性→场景→总结的模板） → 好：按问题链路、排查顺序或决策链路组织

### 中文特有句式
- 坏："进行＋动词"（"对系统进行全面测试"、"进行配置调整"） → 好：直接动词（"全面测试系统"、"调整配置"）
- 坏：被字句堆叠（"被多次报告，被认为可能与……有关"） → 好：施事者已知就改主动句
- 坏：长定语套长定语（"一个十亿参数的开源小模型的微调的完整方案"） → 好：拆成短句，先主干后修饰
- 坏：四字词排比堆叠（"稳定可靠、快速响应、易于维护"） → 好：留一两个，其余用事实说话

### 结尾
- 坏："通过本文，您将能够快速掌握……的核心技巧" → 好：写实际收获、遗留问题或下一步
- 坏：升华拔高（"在未来的技术发展中必将……"） → 好：实在的展望或挖坑（"后面会有更详细的介绍，敬请期待"）

### 格式
- 坏：emoji 当排版符号（✅⚠️📌💡🎯） → 好：用文字（"注意："、"经验法则："）
- 坏："您" → 好："你"
- 坏：工具书式标题（"5 分钟上手"、"高频快捷键速查"、"延伸阅读"） → 好：自然的文章小节名
- 坏：每段都加粗关键词、列表项全是"**小标题**：说明"的机械格式、大量对比表格 → 好：粗体只给真正的关键结论，列表和表格按需使用
- 坏：破折号"——"频繁出现 → 好：多用逗号、冒号或直接拆句

### 内容
- 坏：面面俱到、每个维度都点一遍但都没有细节 → 好：挑重点讲透
- 坏：观点平衡到没有立场 → 好：明确表态，注明这是一家之言
- 坏：论证圆滑到没有破绽 → 好：允许"这块我还没想清楚"、"这里可能是我错了"，真人有立场也有盲区
- 坏：编造链接、版本号、数据 → 好：不确定就不写，或标注需要核实

### 误伤边界（别改过头）
- 否定对比在纠正真实误解时保留："错误发生在保存阶段，而不是上传阶段"是好句子；只在后半句没有证据、纯抬语气时才删
- 有真实功能的连接词和提示保留：流程步骤里的"先……再……"、教程里的"注意："边界条件提示，都是信息不是套话
- 技术术语和正式表达不因"像 AI 词"而删；本博客教程开头的"本文章分享如何在……"是惯例，不是空话
- 只动表达层，不动事实和确定程度："可能"不改成"确定"，不把相关写成因果，不把计划写成已完成
- 原文没有数据时保持概括，不为"具体"编造数字："提升效率"不能改成虚构的"从 2 小时降到 20 分钟"

判断方法与边界规则吸纳自 [stop-slop-zh](https://github.com/wdkang123/stop-slop-zh)、[Humanizer-zh](https://github.com/op7418/Humanizer-zh)、[stop-slop](https://github.com/hardikpandya/stop-slop)，与本博客历史风格融合。
</AI味检查清单>

<写作流程>
## 写作流程

1. **判断文章类型**：教程 / 架构 / 经验 / 选型 / 随笔。用户没说时从素材推断，不反问阻塞
2. **收集真实素材**：可运行的代码、真实仓库链接、真实耗时和数据、踩坑细节。没有的不编造
3. **起草**：套用对应结构模式，开头两三句内进入正题，全程第一人称
4. **修订**：逐条过 AI 味检查清单，重点检查开头、结尾、"您"、emoji、排比句式；最后出声读一遍，听句长节奏和每节收束是否均匀
5. **元数据**：按站点 overlay（若有）或 `references/hexo-frontmatter.md` 写 frontmatter 和文件名；两者都没有时沿用目标站点已有文章的格式
</写作流程>

<自查清单>
## 交付前自查

- 开头三句话内进入正题了吗？
- 全文有"我"的具体经验和判断吗？
- 有具体细节（版本号、耗时、数据、命令输出）吗？
- 段落够短（1-3 句）吗？
- 删掉第一段，文章信息有损失吗？（没有损失就说明开头是铺垫）
- 随便挑几句话，换成任何作者都成立吗？（大部分都能互换就说明缺人味）
- 连续数几句的长度，是不是都差不多？每节结尾是不是都有收束句？
- 逐句问"删掉这句会少什么"，答案经常是"少一点气势"就说明信息密度偏低
- 检查清单逐条过了吗？（尤其：无"在当今"开头、无"综上所述"结尾、无 emoji、无"您"）
- 代码块都标了语言吗？链接都是真实存在的吗？
- 元数据格式符合站点 overlay 或 `references/hexo-frontmatter.md` 的约定吗？（目标站点无 frontmatter 要求时跳过）
</自查清单>

<范例>
## 真实开头范例（摘自历史文章）

**经验型（最常用）**：
> 最近两年技术书的出版速度明显更快了，一个新概念从落地到成书，过去怎么也得一年，现在几个月就出来了。书多了，根本读不过来。

**教程型**：
> 本文章分享如何在 Python 项目中使用 Milvus 向量数据库进行向量存储和检索。

**表态度型**：
> 开门见山，先表明下我的态度吧。以上 4 个是我的首选，个人认为很不错的技术选型。

**经验总结型**：
> 在使用 AI 辅助编程这段时间，发现让 AI 做一些"规模"比较大的编程任务时很容易出现幻觉……

**随笔型**：
> 刚读完《我们为什么需要睡觉？》一书，很有趣。在此摘抄附录：12 条健康睡眠小贴士。
</范例>
