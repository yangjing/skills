# 设计哲学（模块内部设计准则）

> **Status**: active · **Version**: v4（2026-07-30）
> **适用范围**：Bounded Context 内部的代码结构、模块划分与重构判定；规约 Module / Function / Type 粒度的好坏判据
> **规范语言**：BCP 14（RFC 2119/8174）—— MUST、MUST NOT、SHOULD、SHOULD NOT、MAY
> **理论基础**：John Ousterhout《A Philosophy of Software Design》。**本文只承载判据、落地锚点与本文档集内的张力调和，不复述该书的概念讲解**——需要理论背景时读原书
> **本文不重述**：跨边界契约面 → [SPECIFICATION](./SPECIFICATION.md)；命名词表与禁用词清单 → [naming-conventions](./naming-conventions.md)；服务依赖 → [service-dependency-contract](./service-dependency-contract.md)

## 0. Agent 执行协议

1. **Trigger**：评审模块设计、判定是否重构、新增 service / module / class、**写或改代码注释**、或 PR review 需要判断代码质量时，MUST 加载本文。
2. **Load**：按气味索引（§12）定位对应准则章节；MUST NOT 通读全文。
3. **Apply**：本文给判据，[naming-conventions](./naming-conventions.md) 给可执行词表；两者冲突时以后者的词表为准。
4. **Conflict / Stop**：本文准则与跨边界契约要求冲突时，以 [SPECIFICATION](./SPECIFICATION.md) 为准并在此记录调和（§13）。
5. **Output**：PR 描述 MUST 标注触发的气味编号（§12 A-L）；连续 ≥3 项 MUST 回炉设计两次（§7）。
6. **MUST NOT**：MUST NOT 用本文的抽象准则替代具体词表检查；MUST NOT 把项目实践写成通用准则。

## 1. 复杂度症状（重构触发器）

任一症状出现，SHOULD 立刻进入设计回炉而非继续叠加功能：

| 症状 | 定义 | 可观察信号 |
| ---- | ---- | ---------- |
| 变更放大 | 微小功能改动需修改多个文件 | 一个 bug fix PR 触及 ≥5 个 service / module |
| 认知负载 | 修改一行需要记住十几个上下文概念 | 新人 onboarding 1 周内无法独立改动 |
| 未知的未知 | 不知道自己该知道什么 | 改 A 模块时意外破坏 B 的隐式约定（最危险） |

复杂度累积在最常修改、最常阅读的少数代码中；优化这部分的回报远高于均匀重构。

**落地锚点**：按 feature 边界拆分大页面 / 大模块，目标是缓解**认知负载**，而非追求「小函数」（§13.2）；「设计待决策」登记机制的本质是把**未知的未知**显式化，未登记的设计悬空项 SHOULD 视为该症状的隐性存量。

## 2. 战略式编程基线

- MUST 在每个任务中预留 10-20% 时间用于设计与重构
- MUST NOT 以「先把功能做出来」为由跳过模块划分
- 技术债 / 安全硬化 MUST 直接修复，禁止挂账到「设计待决策」清单
- 难度大或过于复杂的技术债 SHOULD 输出原因 + 建议供决策，而非沉默累积

## 3. 模块深度（深 vs 浅）

目标形态 = **窄接口 + 厚实现**：接口的认知成本小，实现隐藏的复杂度大。

### 3.1 评估方法

新增 service / module / class 时 SHOULD 评估「接口规模 vs 实现规模」比：

- 接口（公共方法 + 参数）规模 ≈ 实现规模 → 浅模块，需要回炉
- 接口规模 << 实现规模 → 深模块，符合目标

### 3.2 浅模块气味（MUST 避免）

| 气味 | 信号 | 反例 |
| ---- | ---- | ---- |
| Setter/Getter 包装 | 类的唯一职责是暴露字段 | 全字段透传的 DTO wrapper |
| 透传方法 | 唯一目的是调另一方法 | `service.foo()` → `repo.foo()` 无增值 |
| 参数爆炸 | 15 个布尔参数控制 3 种行为 | `cache.new(size, ttl, evict, shard, hash, ...)` |
| 小函数狂热 | 简单业务被切碎成 3 行函数链 | 10 行 CRUD 拆成 5 个函数（判据见 §13.2） |
| 连体方法 | 必须按序调用 A 再 B | `conn.handshake()` 必须先于 `conn.read()` |

### 3.3 与相邻规范的投射

- [service-dependency-contract §4.2](./service-dependency-contract.md#42-protobuf-作为共享类型定义推荐)「Protobuf 是契约 SSOT，但不统一服务内领域模型」= 深模块原则在服务级的投射：浅契约 + 深实现。
- [SPECIFICATION §7.5](./SPECIFICATION.md#75-服务方法粒度contract-surface-收敛强制) 服务方法粒度 = 本节在跨边界契约面的具体化：逐状态跃迁切分产生的正是「接口规模 ≈ 实现规模」的浅接口。

## 4. 信息隐藏与泄漏

设计决策、数据格式、算法若完全藏在一个模块里，修改时只改一处；反之即「信息泄漏」。四类泄漏 MUST 识别并消除：

| 类型 | 症状 | 修复方向 |
| ---- | ---- | -------- |
| 信息共享 | 文件 A 写字段顺序 V2，文件 B 读时硬编码同顺序 | 抽到单一序列化封装 |
| 时序耦合 | `conn.handshake()` 必须先于 `conn.read()` | 内部自动协商，对外单方法 |
| 时间分解 | Parser → Validator → Saver 强耦合中间结构 | 按「事」分解而非按「步骤」分解 |
| 配置泄漏 | `new(size, ttl, evict, shard, hash, ...)` 让调用者操心内部细节 | 收敛参数 + 合理默认 |

**落地锚点**：配置映射表 MUST 显式标注「不适用 / 无映射」的意图，避免调用方猜测缺失值是漏配还是设计决定；schema 字段顺序变更必须触发契约重新生成——顺序知识只存在于生成链一处，是信息共享泄漏的反向修复。

## 5. 复杂度下沉（Author Pain > Caller Pain）

模块作者承受复杂度 **1 次**，使用者承受 **N 次**。设计取舍 SHOULD 让作者更累、调用方更省心。

**配置项决策树**（面对「是否暴露参数」）：

1. 这个决定是否真的需要不同调用者给出不同答案？否 → 消化在模块内，给合理默认；是 → 进入第 2 步。
2. 90% 场景能否用合理默认覆盖？能 → 只暴露默认值 + 10% 特殊参数；不能 → 必要参数。

**落地锚点**：[SPECIFICATION §15.5](./SPECIFICATION.md#155-全量获取豁免) 全量获取豁免（规范作者多写一条豁免条款，调用者不必为每个 list RPC 写分页逻辑）；[SPECIFICATION §7.4](./SPECIFICATION.md#74-审计字段规范强制) 审计字段内嵌而非 `message AuditFields` 组合（作者写 4 个字段一次，所有调用方零成本）。

## 6. 把错误从语义里消除（Define Errors Out of Existence）

不要「处理」异常，而让异常**根本不可能发生**——重新设计 API 语义，把边界情况变成正常情况。

| 场景 | 错误设计 | 消除式设计 |
| ---- | -------- | ---------- |
| 删除不存在元素 | 抛 `NotFoundException` | 静默成功（删除幂等：已不在 ≡ 刚被删） |
| 文件读到末尾 | 抛 `EndOfFileException` | 返回 0 字节（自然终止） |
| 查询不到值 | 抛 `NotFoundException` | 返回 `Option<T>` / 空集合（强制类型系统表达） |

- MUST 优先重新设计语义而非添加 try/catch。
- MUST NOT 为「看起来健壮」而抛异常——每多一条异常路径，调用方多一条必须考虑的分支。
- 与 [SPECIFICATION §7.2 Connect 错误码](./SPECIFICATION.md#72-connect-协议南北向--东西向默认) 的分工：错误码体系规定**如何返回错误**，本节规定**何时不应该返回错误**。

**落地锚点**：[naming-conventions §8.3](./naming-conventions.md#83-列表-vs-详情字段差异化授权--obligationmask_fields) 把列表 vs 详情的字段差异化授权收敛到单一 `:read` + `Obligation.mask_fields`，而非拆 `:list` / `:get`——避免「列表无权限但详情有权限」的 401 vs 200 分叉。

## 7. 设计两次（Design It Twice）

跨边界 / 跨模块 / 难以撤销的设计 MUST 至少列 2 个候选方案再决策：

1. 方案 A：最直观方案（通常对，但常忽视边界）
2. 方案 B：「听起来很怪」的方案（暴露 A 的隐患）
3. 方案 C：A + B 的取舍组合（往往是最终选择）

- 候选方案 MUST 包含一个非显然方案（哪怕被秒否），用于反衬默认方案的盲点。
- **时间窗口**：在**契约冻结之前**进行。契约冻结进入实施阶段后不再做第二方案——此时反复换方案是「契约先行」的反模式（详见 §13.3）。

**落地锚点**：契约冻结前的强制门槛见 [SPECIFICATION §4.5](./SPECIFICATION.md#45-设计两次门槛契约冻结前)；「设计待决策」清单 + 触发条件段是本节的工作流落地；评审环节的分角色对抗机制是设计两次的工具化形式。

## 8. 注释先写法（Comments-First）

1. 写**接口注释**：函数 / 类对外承诺什么（参数语义、返回值、副作用、错误条件）
2. 读注释挑刺：别扭处暴露 API 设计问题，回头改 API 而非加注释解释
3. 写实现
4. 补内部注释：只解释代码看不出的事

**反模式（MUST NOT）**：注释复述代码（`// 把 x 加一`）；接口注释讲实现细节（调用方不该知道）；把 issue ID / 调用者 / fix 历史写进注释（属于 PR 描述与 git log）。

### 8.1 AI 生成代码的等价映射

当大部分代码由 AI 生成时，上述四步的执行者与形式变化如下：

| 原始步骤 | AI 时代对应 |
| -------- | ----------- |
| 写接口注释 | 写 prompt：告诉 AI 参数语义 / 返回值 / 副作用 / 错误条件 |
| 读注释挑刺，回头改 API | review AI 生成的签名与契约，看它的理解是否暴露 API 设计问题 |
| 写实现 | AI 写实现 |
| 补内部注释 | 同上——AI 生成的实现通常结构显然，内部注释保留得更克制 |

**关键动作**：prompt 里的 contract spec SHOULD 提炼总结后写入代码的 `///` / `/** */` 注释（不要原样粘贴 prompt，prompt 常含示例 / 实现暗示 / 对话语言，撞上文「接口注释讲实现细节」反模式）。该注释是**人类 review 与后续 AI 迭代的共同锚点**：缺失则下一轮 AI 修改无 spec 可对照，容易出现「AI 改一处，契约悄悄漂一格」。

**适用边界**：`pub fn` / trait / RPC handler / 模块顶部 → 接口注释价值不变甚至更高（AI 代码 review 负担重，需可读 spec 锚点）；内部实现 → 更应严格执行「默认不写注释」基线（§13.1），避免 AI 倾向生成的复述式注释。

### 8.2 注释的两个抽象方向

注释 MUST 与代码处于**不同**抽象层次；与代码同层即复述（§12 气味 I）。有效方向只有两个：

| 方向 | 承载 | 判定信号 |
| ---- | ---- | -------- |
| 向上（更抽象） | 意图与理由：为何走这条路、放弃了哪个方案及原因、调用方须知的契约 | 读实现能答「做了什么」，答不出「为何值得这样做」 |
| 向下（更精确） | 代码无法编码的精度：单位、区间开闭、时区与基准、不变式、并发与顺序假设、外部系统怪癖 | 签名与类型拦不住错误调用，错用不报编译错 |

「向下」方向最常被漏写——它不解释代码，而是补上**类型系统表达不了**的约束：`timeout: u64` 的单位、`range(a, b)` 的开闭、retry 是否幂等。这类约束能进类型时 MUST 先进类型（§6），进不了才写注释。

### 8.3 腐化禁令

注释唯一的失效模式是与代码脱钩，而脱钩后的注释**比没有注释更糟**——读者会信它。

- 改代码 MUST 同步改注释。**注释与代码不符按 bug 处理**，MUST NOT 归为风格问题延后
- 注释掉的代码 MUST NOT 提交：历史归 git，留在源码里读者无法判断哪一段生效
- 引用规范 / 决策口径 MUST 用**指针**（章节锚点、决策编号），MUST NOT 复述正文——复述即第二份真相源，必然与 SSOT 漂移
- 装饰性分隔 banner / ASCII 大标题 MUST NOT 用来替代模块拆分：需要视觉分隔就是文件该拆的信号（§1 认知负载）

## 9. 命名判据

模糊名字是模糊思维的化石——写不出精确名字往往意味着设计未想清。此时 MUST 回头改设计，MUST NOT 用注释补偿。

| 承担 | 归属 |
| ---- | ---- |
| 判据：何为好名字、为何模糊名是设计缺陷 | 本节 |
| 清单：禁用词表 + PR review 说明义务 | [naming-conventions §11.2](./naming-conventions.md#112-禁用模糊词)（**唯一真实源**） |
| 结构：casing、词表、跨层字段映射 | [naming-conventions §1](./naming-conventions.md#1-三层命名分工强制) / [§3](./naming-conventions.md#3-casing-与分隔符强制) / [§9](./naming-conventions.md#9-字段映射写法概念层--apischema--策略契约) |

## 10. 一致性（Consistency as a Tool）

一致性是大系统中消除「未知的未知」的最强武器：读者一旦在 A 处理解了某个模式，在 B / C / D 处可零成本复用。

可执行约束——新概念查重、造新词的 PR 门槛、跨模块同名纪律、一致性与局部最优冲突时的取舍——见 [naming-conventions §11.1](./naming-conventions.md#111-一致性优先)（**唯一真实源**），本节不重述。

## 11. 代码显而易见（Obvious Code）

判定标准 = 陌生 reviewer **不需追问**就能理解为什么这样写。若某段代码 reviewer 追问「为什么这么写」，作者 MUST 先回答自己——答案要么进注释（隐式约定），要么改成 obvious 写法。

反模式：「聪明」但隐晦的写法（位运算压缩布尔、宏展开掩盖意图、链式 closure 隐藏 side effect）；依赖语言冷门特性作为常规手段；注释为「妙手」辩护——妙手往往是 obvious 的反义词。

## 12. 十二种气味（Red Flags）

任一气味出现 SHOULD 在 PR review 显式标注；连续 ≥3 个 → MUST 触发「设计两次」（§7）回炉。

| 编号 | 气味 | 信号 | 修复方向 |
| ---- | ---- | ---- | -------- |
| A | 浅模块 | 接口规模 ≈ 实现规模 | §3 增厚实现或合并 |
| B | 信息泄漏 | 多模块知道同一秘密 | §4 抽到单一封装 |
| C | 时间分解 | 按「X 再 Y」分解而非按「X 这事」分解 | §4 按事分解 |
| D | 过度暴露 | 大多调用都用同一特殊参数 | §5 改默认值 |
| E | 透传方法 | 唯一目的是调另一方法 | §3 删除或增值 |
| F | 重复逻辑 | 同样处理多处出现 | 提取公共点 |
| G | 特殊混通用 | 通用模块堆特定代码 | 拆分特化层 |
| H | 连体方法 | 必须按序调 A 和 B | §4 内部自动协商 |
| I | 注释复述 | 「把 x 加一」式无信息量注释 | §8 删除或重写为 why |
| J | 接口讲实现 | 调用方不该知道内部细节 | §4 隐藏实现 |
| K | 含糊名字 | data / handle / process / manager | §9 改精确名 |
| L | 难以描述 | 写不出清短接口注释 | §8 回头改设计 |

## 13. 与相邻规范的张力调和

本文准则与相邻工程规范存在 3 处表面冲突。本节给出裁决口径，使 review 不必重复争论「按哪个规范」。

### 13.1 「注释先写」vs「默认不写注释」

| 维度 | 「默认不写注释」基线 | 本文 §8 |
| ---- | -------------------- | ------- |
| 时机 | 事后（实现完之后） | 事前（设计阶段） |
| 对象 | 实现细节注释 | 接口契约注释（函数 / 类对外承诺） |
| 反对 | 复述代码、过时风险 | API 设计未想清 |

**统一立场**：注释只承载非显然的 why（hidden constraint / invariant / 历史包袱 / 接口契约）。不论事前事后，**注释复述代码**都是反模式。

### 13.2 「小函数狂热」vs 按 feature 边界拆分大文件

| 维度 | 小函数狂热（反模式） | feature 边界拆分（合理） |
| ---- | -------------------- | ------------------------ |
| 触发 | 行数为目标（>30 必拆） | 认知负载为目标（§1 三大症状之一） |
| 单位 | 函数（3-10 行） | page / component / feature 边界 |
| 结果 | 切碎到无信息量 | 按 feature 边界归类 |

**统一立场**：拆分目标是**模块深度**与**认知负载下降**，不是「函数行数」或「组件行数」达标。按 feature 边界拆分符合 §1；若拆出 3 行函数链则违反 §3.2。

### 13.3 「设计两次」vs 契约先行

| 阶段 | 行为 |
| ---- | ---- |
| 设计待决策阶段 | 设计两次主战场，候选方案在此对决 |
| 契约冻结阶段 | 锁定一个方案，不再回滚 |
| 实现阶段 | MUST NOT 换方案 |
| 联调发现契约缺陷 | MUST 回到契约层修订（仍是设计两次的延伸），MUST NOT 仅在实现层补丁 |

**统一立场**：设计两次属于**契约冻结前**的强制门槛；契约冻结后所有修订仍走契约层，但不再做平行候选。两者目标一致——把决策前置到设计阶段，避免实现期反复返工。
